# Проект: поиск источников по arXiv (math) + аналитика и поиск научного руководителя

**Курс:** BIU 8688697201 Data Science — финальный проект
**Команда:** 2 человека

## Идея

**Основная задача — помощь в поиске источников/литературы.** Студент-математик формулирует тему на естественном языке и получает релевантные статьи по смыслу (не по ключевым словам) плюс grounded-ответы со ссылками на конкретные источники — то есть закрывает реальную боль "с чего начать литобзор". Всё остальное — приятные дополнительные фичи поверх того же пайплайна и индекса, не основная цель.

Берём метаданные научных статей с arXiv по вероятности/статистике и дискретной математике/оптимизации (2023–2026), строим пайплайн обработки, индексируем в Elasticsearch с векторными эмбеддингами.

1. **Семантический поиск по темам + RAG (основная функция).** Находит релевантные статьи по смыслу и отвечает на вопросы на естественном языке со ссылками на конкретные источники — инструмент для поиска литературы.
2. **Аналитика трендов (бонус).** Какие темы растут (по числу статей и по цитированиям), кто больше всего публикуется.
3. **Поиск научного руководителя (бонус).** По интересам находит наиболее активных и цитируемых исследователей в этой области, и честно помечает, если институциональная принадлежность (в т.ч. израильская) не подтверждена данными, а не выдумывает её.

## Датасет

arXiv metadata (Cornell University, Kaggle / Google Cloud Storage). JSON-объекты: id, title, authors, categories, abstract, update_date, versions. Полный датасет — 2.2 млн статей, ~3.5 GB. Для проекта берём подвыборку: категории math.PR, math.ST (вероятность/статистика) и math.CO, math.OC (дискретная математика/оптимизация) за последние 3 года (десятки тысяч статей вместо миллионов). Выбор осмысленный — это близкие автору проекта области математики, что облегчает проверку качества поиска и ответов RAG.

## Часть A — пайплайн

1. Сырые метаданные (уже отфильтрованные по категории/дате) → продюсер публикует каждую статью как отдельное сообщение в Kafka-топик `arxiv-papers` — имитация потокового поступления новых препринтов (`kafka_producer.py`).
2. Консьюмер вычитывает топик в файл (`kafka_consumer_to_file.py`) — реальные producer/consumer, а не прямой Spark-Kafka коннектор (тот хрупкий из-за версий Scala/JAR, риск сломаться перед сдачей не стоил того).
3. Spark читает результат, чистит текст, джойнит с данными о цитированиях (Semantic Scholar), считает KPI: число статей по годам/категориям, топ-авторы, динамика конкретных тем (`spark_kpis.py`).
4. Результат — CSV-таблицы (и статьи с эмбеддингами — в Elasticsearch, основной репозиторий данных и источник для семантического поиска/RAG).

## Часть B — AI-компонент

Два взаимодополняющих варианта из списка курса:

- **Эмбеддинги + семантический поиск.** Для каждой статьи считаем вектор локальной моделью (sentence-transformers, без стороннего API), храним в Elasticsearch `dense_vector`. Поиск по смыслу вместо ключевых слов.
- **RAG.** По вопросу пользователя на естественном языке находим top-k релевантных абстрактов (kNN-поиск) и просим LLM ответить, опираясь только на них, с указанием, из каких статей взят ответ.

**Поиск научного руководителя (`find_advisor.py`)** — надстройка над RAG: по интересам пользователя расширенно ищем релевантные статьи, через Semantic Scholar API получаем точных авторов (по authorId) и их аффилиацию. Дизайн-принцип: аффилиацию (в т.ч. израильскую) показываем только если она подтверждена данными — если нет, исследователь всё равно рекомендуется по заслугам (число статей + цитирований по теме), но без выдуманной привязки к вузу. Проверили на практике: из топ-15 кандидатов по "Markov chains" + "random graphs" ни у одного не оказалось подтверждённой аффилиации в Semantic Scholar (типичная проблема — поле self-reported и часто пустое), система корректно не стала ничего придумывать. Хороший живой пример на защиту про раздел брифа "validate AI-generated content, не выдавай непроверенное за факт".

## Выбор модели эмбеддингов — методология и результаты

Модель для эмбеддингов выбирали не произвольно, а через сравнение кандидатов на нашей собственной подвыборке данных — это отдельный содержательный кусок для дизайн-документа и презентации.

**Кандидаты:** `all-MiniLM-L6-v2` (маленькая, быстрая, общего назначения), `all-mpnet-base-v2` (крупнее, обычно качественнее по бенчмаркам), `allenai-specter` (обучена специально на научных статьях через граф цитирований). Плюс `TF-IDF` как классический keyword-baseline.

**Методология (3 итерации, скрипты сохранены):**

1. `compare_embedding_models.py` — первая версия: самодельная метрика `category_overlap@10` (доля из 10 ближайших соседей статьи, у которых совпадает категория arXiv).
2. `evaluate_embeddings.py` (первая ревизия) — добавили title→abstract retrieval (self-supervised: заголовок статьи как запрос, её собственный абстракт — заведомо правильный ответ; метрики MRR, Recall@1, Recall@10) и TF-IDF baseline, чтобы явно показать разницу между семантическим и keyword-поиском.
3. `evaluate_embeddings.py` (финальная версия) — заменили самодельную метрику на стандартные из общепринятых бенчмарков embedding-моделей (MTEB / BEIR): **nDCG@10** для retrieval-задачи и **V-measure / NMI** через k-means-кластеризацию для оценки того, насколько хорошо эмбеддинги разделяют тематику (аналог MTEB Clustering task).

**Итоговая таблица (выборка 5000 статей):**

| Модель | dim | MRR | R@1 | R@10 | nDCG@10 | V-measure | NMI |
|---|---|---|---|---|---|---|---|
| all-MiniLM-L6-v2 | 384 | 0.892 | 0.848 | 0.962 | 0.908 | 0.485 | 0.485 |
| **all-mpnet-base-v2** | **768** | **0.904** | **0.864** | **0.971** | **0.920** | **0.623** | **0.623** |
| allenai-specter | 768 | 0.549 | 0.465 | 0.703 | 0.580 | 0.532 | 0.532 |
| TF-IDF (baseline) | 21636 | 0.809 | 0.739 | 0.935 | 0.838 | 0.335 | 0.335 |

**Решение: `all-mpnet-base-v2`** — единственная модель, лучшая сразу по всем метрикам (и retrieval, и clustering), без компромиссов.

**Ключевые находки для презентации:**

- Семантические эмбеддинги заметно превосходят keyword-поиск (TF-IDF) — особенно на кластеризации по теме (V-measure 0.623 против 0.335, почти вдвое), что напрямую отвечает на вопрос брифа "зачем нужен семантический поиск вместо keyword search".
- `allenai-specter`, несмотря на то что обучена специально на научных статьях, показала худший retrieval (хуже даже TF-IDF) при неплохом clustering. Объяснение: specter обучена представлять title+abstract как единый документ (для сравнения через цитирования), а не сопоставлять короткий запрос (title) с отдельным документом (abstract) — то есть её сильная сторона не совпадает с нашей задачей поиска по запросу. Хороший пример понимания архитектурных различий моделей, а не просто "взяли то, что лучше по одной цифре".

## KPI/тренды — на что обратить внимание при подаче на слайдах

- **Citation lag.** В `kpi_keyword_trends.csv` среднее число цитирований по каждой теме монотонно падает от 2023 к 2026 — это не спад интереса к теме, а естественный эффект возраста статьи (у статьи 2023 года было 3 года на накопление цитирований, у статьи 2026 — почти ноль). Тренд по **числу статей** (`paper_count`) — честный индикатор роста/спада интереса; `avg_citations` стоит подавать с этой оговоркой или сравнивать только "устоявшиеся" годы (2023-2024).
- Имена авторов в сырых метаданных arXiv хранятся в LaTeX-escaped виде (`Klav\v{z}ar`) — чистим через `pylatexenc` перед выгрузкой в `kpi_top_authors.csv`.
- `kpi_keyword_trends.csv` теперь содержит колонку `reliable` (paper_count ≥ 5) — не показываем на слайдах avg_citations для строк с малым n (например, 1 статья за год — это не тренд).
- Список терминов для трендов (`Markov chain, martingale, branching process, random walk, random graph, graph coloring, hypothesis testing, linear programming, convex optimization`) явно подтверждён как пройденный на бакалавриате — можно уверенно защищать на вопросах.
- Сравнение полного прогона (все 4 категории) с прогоном только по CO+OC оказалось хорошей проверкой корректности: PR-темы (Markov chain, random walk, branching process) сильно просели при фильтре на CO+OC, а OC/CO-темы (linear programming, convex optimization, graph coloring) остались почти без изменений — совпадает с ожиданиями по структуре математики, хороший аргумент "мы валидировали не только технически, но и по домену".

## Технологии курса, которые закрываем

**Docker.** Elasticsearch и Kafka подняты как настоящие Docker-контейнеры (`docker run ...`) — реальная контейнеризация, не имитация.

**NoSQL / Elasticsearch.** Основной репозиторий данных: индекс `arxiv_math`, все 57к статей + поле `dense_vector` для векторного поиска (cosine, kNN). Используется в `build_index.py` (загрузка), и на нём построены `search.py`, `rag_answer.py`, `find_advisor.py`, `find_theorem.py`.

**Streaming / Apache Kafka.** Настоящий producer/consumer (не Spark-Kafka коннектор — сознательно, из-за хрупкости Scala/JAR-зависимостей). `kafka_producer.py` публикует каждую статью как отдельное событие в топик `arxiv-papers`; `kafka_consumer_to_file.py` вычитывает их обратно в файл `data/arxiv_math_from_kafka.jsonl`, который потом читает Spark. Проверено сверкой количества: 57 155/57 155. Важно точно: это **одноразовый replay** уже готового статического датасета через настоящий брокер (демонстрирует технологию), а не live-подписка на новые препринты arXiv — так и написано в докстринге `kafka_producer.py`. `build_index.py` (индекс для поиска/RAG) читает исходный отфильтрованный файл напрямую, минуя Kafka — через Kafka идёт только путь к Spark-KPI.

**Настоящее live-обновление (poll_arxiv_live.py + consume_arxiv_live.py).** Отдельная пара скриптов и отдельный топик `arxiv-papers-live` — сознательно не смешаны с историческим replay'ем выше. `poll_arxiv_live.py` реально стучится в `export.arxiv.org/api/query` по каждой из 4 категорий; точка отсчёта — дата самой свежей статьи, уже лежащей в нашем датасете (`data/arxiv_math_subset.jsonl`), а не произвольное окно от "сейчас" — так первый же реальный запуск сразу находит всё, что вышло после сбора датасета. Дальше состояние трекается в `data/live_poll_state.json` per-категория. `consume_arxiv_live.py` вычитывает топик (с `group_id`, иначе Kafka не запоминает прочитанное), дедуплицирует по id (Kafka producer — "at least once", дубль сообщения — штатная ситуация), кодирует каждую новую статью той же моделью и делает upsert прямо в существующий индекс `arxiv_math` через `es.index()` — без пересборки всего индекса.

**Проверено на реальном запуске.** Датасет собирался с cutoff 30 июля; первый прогон `poll_arxiv_live.py` нашёл 187 реально новых статей за это время по всем 4 категориям, `consume_arxiv_live.py` их проиндексировал, и `search.py "Rainbow percolation"` тут же нашёл статью от 13 августа 2026 (Peter Gracar, Benjamin Lees) первым результатом — статьи, которой не было в датасете на момент сбора. Полная цепочка arXiv API → Kafka → эмбеддинг → Elasticsearch → поиск подтверждена на живых данных, не на симуляции.

**Batch vs streaming.** Приём через Kafka — потоковый паттерн (событие на статью). Обработка в Spark — батчевая (весь файл разом за один проход). Оба паттерна присутствуют осознанно, не перепутаны.

**Apache Spark (`spark_kpis.py`).** Читает файл, полученный из Kafka, join с данными о цитированиях (Semantic Scholar), считает: статьи по категориям/годам, топ-авторы (explode+groupBy), тренды по ключевым терминам с колонкой `reliable`. Это и есть обязательный "meaningful transformation" шаг курса.

**RESTful API.** Semantic Scholar Graph API (`fetch_citations.py`, `find_advisor.py`, `find_theorem.py`) — цитирования, авторы, поиск, ссылки на источники; Elasticsearch REST API (через python-клиент); Ollama REST API (локально).

**ETL/ELT — гибрид, осознанно.** `filter_math_subset.py` — Transform до Load (классический ETL: фильтрация по категориям/дате ДО того как данные попадают в Kafka/индекс). Spark-этап — Transform ПОСЛЕ Load (данные уже лежат в файле/Kafka, дальше агрегируются) — уже ELT-паттерн. На защите можно явно показать понимание разницы, а не запутаться.

**AI-стек (часть B):** эмбеддинги (all-mpnet-base-v2, обоснован через MTEB/BEIR-метрики), семантический поиск, RAG (Ollama, llama3.1:8b, обоснован через сравнение с 3B), плюс два honest-by-design бонуса (advisor finder, theorem/citation-hop finder).

**Что сознательно не используем и почему это ок:** HDFS, object store (S3/MinIO), табличные форматы (Iceberg), SQL/RDBMS, MapReduce/ZooKeeper/Sqoop/Pig/Oozie, графовые БД. Бриф требует минимум одну технологию из списка части A — Elasticsearch с запасом закрывает это требование, плюс Kafka и Spark сверху. Классический Hadoop-стек (MapReduce/Pig/Oozie) не берём сознательно: современная связка Spark+Kafka+Elasticsearch на практике его заменяет — это стоит проговорить на защите как понимание архитектурных альтернатив, а не пробел в знаниях.

## Почему это лучше, чем просто спросить ChatGPT

Ожидаемый вопрос на защите — готовый честный ответ на пять пунктов:

1. **Привязка к проверяемым источникам.** Каждый ответ RAG-системы прослеживается до конкретной статьи с id — можно пойти и проверить. Обычный чат-бот смешивает то, что помнит из обучения, с тем, что может сам придумать, без прозрачного способа отличить одно от другого. Мы это показали на практике: llama3.2 (3B) дала расплывчатый ответ с фразами, скопированными из одного абстракта, а llama3.1 (8B) с тем же RAG-промптом — заметно более глубокий синтез с честным указанием источников.
2. **Актуальность на узкой теме.** Общая модель обучена на снэпшоте интернета с задержкой и не индексирует систематически все статьи по math.PR/ST/CO/OC за последние месяцы — у нас конкретный, полный срез именно этой области за последние 3 года (57 155 статей), плюс отдельный механизм реального live-обновления (`poll_arxiv_live.py` + `consume_arxiv_live.py`, см. ниже) — проверено на реальных данных: 187 статей, вышедших после сбора датасета, найдены и проиндексированы через настоящий arXiv API. Основной replay через `kafka_producer.py` при этом остаётся статическим одноразовым срезом — это два разных, сознательно не смешанных механизма.
3. **Вычисляемая, а не угадываемая аналитика.** Тренды по годам и цитированиям — это реальные агрегаты по реальным данным (Spark + Semantic Scholar), а не текст, который LLM сочиняет правдоподобно похожим на статистику.
4. **Честный отказ от галлюцинаций там, где данных нет.** Наглядно видно на примере поиска научного руководителя: система прямо говорит "аффилиация не подтверждена", вместо того чтобы выдумать вуз — что вполне может сделать голый чат-бот, если его просто спросить "кто занимается X в Израиле".
5. **Приватность и стоимость.** Всё крутится локально через Ollama, без утечки запросов в третьи руки и без платы за токены.

## Поиск доказательства теоремы (find_theorem.py)

Развитие RAG: вместо абстрактов скачивает **LaTeX-исходники** топ-8 релевантных статей напрямую с arXiv (`arxiv.org/e-print/{id}`), извлекает через регулярки блоки `\begin{theorem}`, `\begin{lemma}`, `\begin{proof}` и т.п., ранжирует их по смыслу относительно вопроса. На практике находит настоящие формулировки теорем дословно из текста, не выдумывая.

**Citation hop (один шаг).** Если внутри найденного блока есть `\cite{...}`, парсим библиографию той же статьи (`.bbl`/`.bib`) и резолвим цитату — если результат не оригинальный, а позаимствованный, это видно явно. Проверили на примере с неравенством Хёффдинга: система правильно нашла блок, содержащий `\cite{Hoeffding1994}`, и LLM корректно связала конкретную формулировку с первоисточником — через блоки статьи. Дальше одного шага цепочку намеренно не разворачиваем — точность быстро падает.

Известные технические ограничения: не все статьи используют классический BibTeX (`biblatex` даёт `.bbl` в другом формате, не распознаётся); Semantic Scholar иногда рейт-лимитит обогащение цитаты — есть retry с backoff, но это лишь бонусное обогащение (сама цитата всё равно показывается LLM и без него).

## Известные ограничения (для Q&A)

- **Только абстракты, не полный текст.** RAG видит title+abstract, не тело статьи с доказательствами. Вопрос вида "в какой статье доказательство теоремы X" система решает ненадёжно — абстракт часто не содержит явную формулировку теоремы или доказательство. Полнотекстовая индексация (PDF/LaTeX) — отдельный по объёму кусок работы, сознательно оставлен вне scope.
- **Только последние 3 года, только 4 категории.** Классические/старые результаты или статьи вне math.PR/ST/CO/OC система просто не видит — не найдёт и не должна пытаться выдумать.

## Обогащение цитированиями (Semantic Scholar)

Датасет arXiv metadata не содержит числа цитирований, только id/title/authors/categories/abstract/даты. Чтобы связать тренды по ключевым словам с реальным цитируемым импактом, дозагружаем `citation_count` через Semantic Scholar Graph API (batch-эндпоинт, без API-ключа, до 500 id за запрос) — скрипт `fetch_citations.py`, результат в `data/citations.jsonl`, джойним с основным датасетом на шаге KPI.
